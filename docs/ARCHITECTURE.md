# TESSA Matrix Studio — техническая архитектура

Этот документ описывает production-логику TESSA Matrix Studio: какие браузерные и TESSA-механизмы используются, как Excel связывается со строками матрицы, где проходят проверки безопасности и в какой момент выполняется запись.

## 1. Что это за приложение

TESSA Matrix Studio — userscript для Tampermonkey. Он выполняется прямо на странице TESSA в браузере текущего пользователя и добавляет отдельную панель для сценария:

`TESSA → свежая выгрузка XLSX → изменение Excel → Preview → свежий preflight → подтверждение → Apply → повторная проверка`.

Studio не является отдельным сервером и не имеет собственного backend. Он не получает дополнительных прав: все CardGet/CardNew/CardStore/CardRequest выполняются в пользовательской сессии TESSA и подчиняются штатным правам и состоянию карточки.

## 2. Модель выполнения и зависимости

Production-файл — `tessa-matrix-studio.user.js`.

Ключевые свойства userscript:

- `@grant none` — Studio выполняется в контексте страницы. Это сделано намеренно, потому что TESSA bridge использует уже загруженные на странице внутренние JS-объекты TESSA;
- `@require` отсутствует — production-код не подтягивает внешние JavaScript-библиотеки во время работы;
- область запуска ограничена адресами TESSA, перечисленными в metadata-блоке;
- автообновление Tampermonkey разделено на маленький metadata-файл (`@updateURL`) и полный userscript (`@downloadURL`), оба публикуются через GitHub Releases.

Основные браузерные API: `Blob`, `ArrayBuffer`, `TextEncoder/TextDecoder`, `CompressionStream/DecompressionStream`, `IndexedDB`, DOM API и штатные Promise/async функции.

## 3. Слои внутри userscript

Файл большой, поэтому внутри него ответственность разделена явными секционными комментариями. Логически приложение состоит из шести слоёв.

### 3.1. XLSX

Studio читает и формирует `.xlsx` без внешней Excel-библиотеки. XLSX рассматривается как ZIP-контейнер с SpreadsheetML-файлами. Код разбирает workbook/sheets/shared strings, формирует XML и при возможности использует браузерные `CompressionStream` / `DecompressionStream`.

Цель этого слоя — превратить рабочую книгу в нормализованные строки и обратно. Он не знает, как TESSA сохраняет карточки.

### 3.2. Справочники

Справочные значения TESSA нормализуются и индексируются для точного поиска по ID/наименованию. Каталог кэшируется в IndexedDB; текущий TTL — 12 часов. Кнопка выгрузки со свежими справочниками принудительно перечитывает значения.

Для сравнения используются типизированные значения. Булево `Да` из Excel и raw `true` из TESSA могут быть семантически равны, но сырой fingerprint исходной строки при этом остаётся отдельным механизмом контроля stale-состояния.

### 3.3. TESSA bridge

`TessaBridge` — единственный слой, который знает детали внутренних API TESSA. Planner и UI не должны обращаться к CardService напрямую.

Bridge использует штатные операции карточек:

- `CardGet` — чтение строк и свежего состояния;
- `CardNew` — получение структуры новой строки;
- `CardStore` — сохранение подготовленной строки;
- `CardRequest` — получение структуры матрицы, проверка дублей и штатное удаление строки специальным request type.

Также bridge получает структуру критериев/функций, данные представлений и скрытые идентификаторы, необходимые для точного сопоставления.

### 3.4. Planner

Planner строит план, но ничего не записывает. Его задача — ответить на вопрос «что именно изменит этот Excel относительно текущей матрицы?».

Базовые действия:

- `NOOP` — строка не меняется;
- `UPDATE` — меняются поля существующей строки;
- `ADD` — создаётся новая строка;
- `REPLACE` — значения одной строки переносятся поверх другой существующей строки по подтверждённой identity-логике;
- `DELETE` — удаляется конкретная существующая строка.

Главный инвариант: Studio не должен угадывать identity. Если служебные идентификаторы неоднозначны, повреждены или не подтверждаются baseline-данными, строка должна стать `SKIP`/blocker, а не превращаться «на глаз» в ADD/DELETE.

### 3.5. Safety / preflight / apply

Это критический слой.

Preview сначала строит план, затем выполняет read-only preflight по свежему состоянию TESSA. Поэтому уже на экране Preview видны строки, которые нельзя безопасно применить: невалидные справочники, дубли, stale-конфликты и зависимые DELETE.

Перед фактической записью Apply выполняет **ещё один свежий preflight**. Preview не считается разрешением на запись навсегда: если между Preview и Apply матрица изменилась, соответствующая операция должна быть пропущена или заблокирована.

Для зависимостей типа `UPDATE/ADD → DELETE` используется отдельное семантическое сопоставление. Если prerequisite-операция не проходит preflight или падает при сохранении, связанный destructive DELETE не должен выполняться отдельно.

Физический DELETE также требует отдельного пользовательского подтверждения.

### 3.6. UI

UI отвечает только за сценарий пользователя: выгрузку, загрузку файла, Preview, выбор отдельных изменений, Apply, прогресс и сообщения. Бизнес-правила сопоставления и запись должны оставаться вне UI.

Preview поддерживает session-only исключения: пользователь может временно не применять отдельное поле UPDATE или целую UPDATE-строку. Исходный Excel и первоначальный план при этом не переписываются.

## 4. Roundtrip XLSX V6

Текущий формат — `TESSA_MATRIX_ROUNDTRIP_V6`.

В рабочей книге есть обычные пользовательские листы и служебные данные. Ключевая идея — Excel содержит не только видимые значения, но и identity, позволяющую доказать, какую строку TESSA редактирует пользователь.

Используются, в частности:

- `MatrixRowID`;
- `MatrixVersionID`;
- Matrix/Template metadata;
- скрытая схема колонок;
- veryHidden-лист `__TESSA_BASELINE`.

Baseline-ledger хранит исходные identity и `BaseFingerprint`. Он нужен для обнаружения повреждения служебных колонок, stale-изменений и безопасного определения физического DELETE.

Поддерживаются старые Roundtrip V1–V5 для чтения, но новые выгрузки формируются в V6.

## 5. Почему нельзя сопоставлять только по номеру строки Excel

Excel можно сортировать, копировать, вставлять и удалять строки. Поэтому позиция `строка 25` не является identity.

Основная опора — скрытые `MatrixRowID/MatrixVersionID` плюс baseline. Позиционные признаки используются только там, где planner может доказать конкретный overwrite-сценарий. Если доказательств недостаточно, безопасное поведение — не записывать.

Это особенно важно для REPLACE и DELETE: ошибка сопоставления здесь может повредить не ту строку.

## 6. Stale-защита

Между выгрузкой Excel и Apply TESSA может измениться другим пользователем.

Для существующих строк Studio хранит исходный fingerprint и перед записью перечитывает текущее состояние. Если изменились данные, на которых базировался Excel, Studio не должна «протащить» старый снимок поверх свежего состояния.

Для copied ADD и REPLACE отдельно проверяется provenance исходной строки: копирование из устаревшего source не должно создавать новую строку из старых данных.

## 7. Частичное применение

Apply рассчитан на то, что одна строка может оказаться невалидной, пока другие остаются безопасными.

Поэтому результат различает:

- применённые операции;
- runtime/preflight skips;
- частичный результат;
- ошибки конкретных строк.

При ошибке Studio автоматически формирует JSON-отчёт `TESSA_Matrix_ErrorReport_*.json`; после Apply формируется отдельный результат применения. В публичный GitHub Issue нельзя без проверки прикладывать рабочие выгрузки, внутренние URL, персональные данные и идентификаторы карточек.

## 8. Производительность

Внутренние операции ограничивают параллелизм, чтобы не устроить всплеск запросов к TESSA:

- параллельные snapshot `CardGet`: 6;
- ZIP compression/decompression: 4;
- TTL preview snapshot: 15 минут.

Это не означает, что Preview можно применять через 15 минут без новой проверки: Apply всё равно выполняет свежий preflight.

## 9. Release pipeline

`Quality & Security` выполняет полный `npm test` и CodeQL.

`Release` запускается только после успешного Quality & Security на `main` либо вручную. Если production-userscript не менялся, публикация новой версии пропускается. Если менялся:

1. повторно выполняется `npm test`;
2. считывается `@version`;
3. запрещается перезапись уже опубликованной версии;
4. собираются userscript, metadata и ZIP;
5. формируется `SHA256SUMS.txt`;
6. создаётся GitHub/Sigstore provenance attestation;
7. создаётся immutable GitHub Release;
8. публичные `releases/latest/download` перечитываются анонимно и проверяются по версии и SHA-256.

Отдельный `Delivery Canary` ежедневно проверяет, что latest assets всё ещё доступны и согласованы.

Внешние GitHub Actions закреплены на полные 40-символьные commit SHA. Dependabot создаёт отдельные PR для обновления этих pin-значений.

## 10. Где менять код

При доработке придерживайтесь границ:

- Excel/ZIP/XML — секция XLSX;
- справочники — dictionary layer;
- TESSA CardService — только `TessaBridge`;
- определение UPDATE/ADD/REPLACE/DELETE — planner;
- stale/duplicate/dependency проверки и запись — safety/apply;
- кнопки/рендер/progress — UI.

Не переносите TESSA API-вызовы в UI и не добавляйте destructive fallback в planner.

Для изменения поведения сначала добавляется regression-тест, который воспроизводит проблему и падает на старом поведении; только после подтверждённого RED меняется production-логика.

## 11. Production-инварианты

Перед merge изменение не должно нарушать следующие правила:

1. Preview не пишет в TESSA.
2. Apply всегда повторяет свежий preflight.
3. Неоднозначная identity не угадывается.
4. Stale source/target не перезаписывается молча.
5. Ошибка prerequisite не оставляет связанный DELETE исполняемым.
6. DELETE требует доказанной identity и отдельного подтверждения.
7. Studio не обходит права TESSA.
8. Публичный релиз не перезаписывается той же версией.
9. Внешние CI Actions не используются по плавающему tag/branch ref.
