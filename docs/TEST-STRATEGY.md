# TESSA Matrix Studio — Test Strategy

Эта стратегия появилась после live-UAT 2026-09-09, когда синтетические тесты проходили, но реальная TESSA приняла два DELETE-запроса без фактического удаления строк, а искусственный post-Apply Store основной карточки был отклонён серверным `CheckRequestStoreExtension`.

Главный принцип: **успешный mock/RPC-ответ не является доказательством результата операции**. Для write-кода проверяется наблюдаемый переход состояния.

## Уровни проверки

### 1. Unit / pure logic

Быстрые детерминированные тесты без TESSA проверяют парсинг XLSX, planner, identity/baseline, диапазоны, словари, построение payload, review и локальные инварианты. Они отвечают на вопрос: «правильно ли Studio рассчитала, что нужно сделать?»

Unit-тесты необходимы, но сами по себе не разрешают внешний релиз write-функций.

### 2. Stateful contract

Stateful contract-тест моделирует состояние до и после операции, а не только факт вызова метода. Для критичных операций обязательны следующие инварианты:

- ADD: отсутствующая строка после принятой записи появляется с ожидаемой semantic identity;
- UPDATE: изменяется нужная server identity, посторонние поля не меняются;
- DELETE: член `MtxRouteMatrixRows` переходит в `Deleted`, сохраняется основная карточка, после readback membership отсутствует;
- main-matrix save: Store содержит реальные changed-state данные; пустой `forceTransaction` не считается сохранением;
- reconciliation: `accepted` и `verified` считаются раздельно; расхождение не может называться успешной записью;
- interval validation: известный `LeftOperandExtractor is null` не превращается в ложное «дублей нет».

Каждый production-баг сначала получает воспроизводимый fixture/contract-test, затем исправление.

### 3. Native runtime evidence

Часть TESSA API и Cherkizovo-расширений не имеет доступного нам стабильного публичного контракта. Здесь нельзя безопасно угадывать по именам методов.

Studio предоставляет opt-in инструменты:

- **Снять интерфейс TESSA** — фиксирует доступные методы editor/cardModel/CardService/контролов и техническую структуру без произвольных бизнес-значений;
- **Начать запись нативного действия / Остановить и скачать** — фиксирует технические CardService-вызовы и membership до/после одного штатного действия пользователя;
- Diagnostics request capture — сохраняет запрос/ответ read-only проверки, включая server validation.

Для неизвестного write-контракта правильный цикл такой:

`штатное действие TESSA → sanitized runtime evidence → контракт → regression test → реализация Studio`.

Запись нативного действия должна быть ограниченной по времени/объёму, восстанавливать перехваченные методы после завершения и по умолчанию редактировать бизнес-значения.

### 4. Native canary / test TESSA

Максимальный уровень достоверности — отдельная тестовая матрица в реальной TESSA с тестовой учётной записью. Canary должен выполнять контролируемый CRUD-roundtrip:

`baseline → ADD → readback → UPDATE → readback → COPY/ADD → readback → DELETE → SAVE → readback → cleanup`.

Публичный GitHub-hosted runner не имеет корпоративной сети/сессии TESSA, поэтому этот уровень должен выполняться на **self-hosted** runner внутри допустимого контура либо отдельным внутренним CI-агентом.

Canary не должен работать на боевой пользовательской матрице. Нужны выделенные тестовые данные, идемпотентный cleanup и минимальные права.

## External release gate

Внешняя версия не должна называться готовой только потому, что `npm test` зелёный. Для write-critical изменений действуют четыре условия:

1. Unit / pure logic — зелёный.
2. Stateful contract — зелёный.
3. Full regression (`npm test`) — зелёный.
4. Для изменённого/неизвестного TESSA-контракта есть актуальное Native runtime evidence или успешный native canary.

Если пункт 4 нельзя выполнить автоматически, сборка остаётся RC и отдаётся только для целевого снятия контракта. После получения evidence оно превращается в fixture/contract-test; только затем возможен внешний release.

## Обязательная матрица покрытия

Машиночитаемая матрица находится в `tests/coverage-manifest.json`. `tests/test-coverage-contract.mjs` проверяет, что write-critical группы имеют unit + stateful contract coverage, runtime-evidence capability, а их контрактные тесты реально входят в `npm test`.

Минимально контролируются: XLSX roundtrip, словари, ADD, UPDATE, DELETE, сохранение основной карточки, post-Apply refresh, reconciliation, support report, interval diagnostics и native runtime recorder.

## Что означает результат Apply

Термины не взаимозаменяемы:

- **planned/requested** — операция вошла в подтверждённый план;
- **accepted** — серверный write-вызов завершился без ошибки или staged-операция была успешно сохранена;
- **verified** — повторное чтение TESSA подтвердило ожидаемое состояние;
- **divergent** — readback показывает состояние, отличающееся от ожидаемого;
- **unknown** — результат нельзя достоверно проверить.

`accepted > verified` — не успех «4 из 4». Пользователь должен увидеть отдельно количество принятых сервером операций и количество реально подтверждённых readback-ом.

## Правило для новых багов

Если пользователь повторно сообщает уже известный класс дефекта, нельзя просто добавить ещё один локальный fix. Сначала проверяется, почему существующий test layer его пропустил. Если причина — уровень абстракции/mocking, добавляется более низкий stateful/native contract test.

Так тестовая база постепенно становится моделью фактического поведения TESSA, а не коллекцией проверок наших собственных заглушек.
