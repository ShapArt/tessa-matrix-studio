# Исправление синхронизации строк 1.12.0

## Что воспроизведено

Исходный файл с изменениями содержит 24 записи в baseline, два отсутствующих исходных ID, три правки, точную копию и изменённую копию после пустых строк. Общий счётчик заполненных строк остался равен 24.

На исходном коде 1.11.11: **3 UPDATE / 1 ADD / 0 DELETE / 20 NOOP**. После исправления на том же файле и исходном baseline: **3 UPDATE / 1 ADD / 2 DELETE / 20 NOOP**. Одна ошибочная ячейка справочника остаётся неприменяемой; остальные корректные поля обновляются.

Причины: проверка разницы количества строк объявляла смешанное удаление и добавление потерей ID; дополнительный запрет копии вместе с исчезнувшей identity отключал удаления. Полная очистка рабочих ячеек также была специально запрещена.

## Правила

- Заполненная новая строка без ID — ADD; промежуточные пустые строки игнорируются.
- Отсутствующий исходный ID — DELETE, независимо от количества добавлений.
- Все рабочие ячейки очищены — DELETE. Отдельные очищенные ячейки остаются правками полей.
- Копия ниже исходной области выгрузки — ADD, даже если суммарное число строк не изменилось.
- Точная копия единственной существующей строки — NOOP; серверная проверка дубликатов сохраняется.
- Нет запрета DELETE по количеству и проценту. Общий предел размера Apply и проверки текущей версии остаются.
- Строки, добавленные в TESSA после исходной выгрузки, не удаляются по отсутствию в старом Excel.

Обновление Excel-схемы сохраняет смешанные добавления и удаления. Повреждённые оставшиеся ID, конфликт версий и неоднозначные справочники по-прежнему требуют исправления.

## Что показывает диагностика после применения

Новая строка из Excel 41 присутствует в снимке матрицы: число строк увеличилось с 24 до 25. Полная копия Excel 38 уже имела эквивалентную строку и не создавала вторую. Оба ожидаемых удаления отсутствовали в старом плане и не выполнялись.

Файл 13 выгружен в 11:21:28; Preview перед применением сохранён около 11:25, диагностика — около 11:27 (московское время). Файл 13 не является доказательством результата этого применения. Старый Excel после применения закономерно конфликтует с уже изменившимися строками; перед следующим изменением нужна новая выгрузка или объединение с текущей матрицей.

## Подтверждение записи

Обычная кнопка Apply теперь автоматически проверяет наличие строк в матрице и совпадение типизированных значений. Успешного ответа Store и открытия карточки недостаточно. `acceptedCount` считает успешные ответы записи; `appliedCount` после сверки считает подтверждённые операции. Неполная проверка или расхождение дают частичный итог. Проверка не выполняет повторный Store или автоматический откат.

Проверка `ValidationResult` остаётся обязательной согласно [документации TESSA по работе с карточками](https://mytessa.ru/docs/3.6/dev/dev/objects/).

## Проверки и открытая проблема

Регрессия `tests/excel-row-lifecycle.mjs` воспроизводит исходный дефект на обезличенных данных и проверяет исправление, пустые промежутки, оба вида удаления, обновление схемы и параллельные изменения. `tests/apply-verification-accounting.mjs` проверяет отсутствие ложного успеха, если созданная карточка не входит в матрицу.

Исходные пользовательские Excel, диагностика, справочники и переписки в репозиторий не включены.

Ошибка `LeftOperandExtractor is null` в серверном ValidateDuplicate остаётся открытой. В приложенной диагностике отрицательный контроль точной копии падает как с CardNewMode.Default, так и с CardNewMode.Valid. Это исправление не отключает серверный контроль и не объявляет проблему решённой. Новая запись с интервалом в действующей TESSA требует отдельной проверки; клиентские тесты её не заменяют.
