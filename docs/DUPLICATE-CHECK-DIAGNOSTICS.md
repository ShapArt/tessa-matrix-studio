# Отказы проверки дубликатов

## Что исправлено в 1.9.47

После частичного Apply Studio показывает не только ошибочные поля, но и отказавшие операции: номер Excel, этап и причину. Отказ предварительной проверки остаётся виден, хотя строка не входит в число запрошенных операций. Длинный список неверных значений Excel больше не скрывает эти отказы.

`TessaBridge.validateDuplicate` требует `ok === true`. Успешный HTTP-запрос или `validationResult.isSuccessful` без явного разрешения больше не допускает Store. Ответ `false` означает обнаруженный дубль; отсутствие/неверный тип `ok` означает некорректный ответ, а не найденный дубль.

| Поле отказа в Apply JSON | Смысл |
|---|---|
| `source: preflight-add` | Добавление отклонено при предварительной проверке |
| `source: store-add` | Отказ на этапе применения; сам по себе не доказывает вызов Store |
| `check: duplicate` | Ошибка возникла внутри проверки дубликатов |
| `writeAttempted: false` | После этой проверки запись данной операции не запускалась |
| `code: duplicate-found` | Сервер явно сообщил о дубле |
| `code: duplicate-response-invalid` | Нет корректного Boolean-разрешения |
| `code: duplicate-interval-extractor` | Сервер вернул `LeftOperandExtractor is null` |
| `code: duplicate-check-failed` | Другая ошибка запроса проверки |

Эти поля добавляет локальный тип `DuplicateValidationError`. Произвольное исключение Store не получает `writeAttempted=false`: потеря ответа после записи означает неопределённый исход и требует чтения результата. Полный текст отказа остаётся в добровольно скачиваемом отчёте и может содержать рабочие значения; не публикуйте исходный JSON в открытом GitHub.

## Что установлено о запросе

Штатный web-клиент из предоставленной выгрузки сайта и Studio используют:

- `CardRequest.requestType = f5c0419f-15cc-428e-b2f9-76c1b3ef7525`;
- `info.card = card.getStorage()`;
- `info.versionId`, `info.matrixId`, `info.templateID` как типизированные Guid;
- `IntValue / IntToValue` типа Int для целочисленного интервала;
- `DecimalValue / DecimalToValue` для Decimal.

Штатный редактор перед проверкой клонирует карточку и переносит изменения из виртуальных таблиц в реальные Values/Roles. Studio сразу записывает изменения в реальные таблицы; перенос виртуальных строк не требуется. Перенос не меняет тип Int на Decimal и не добавляет метаданные оператора к строке значения.

Общий контракт расширяемого запроса описан в [официальном API CardRequest](https://mytessa.ru/docs/4.0/api/html/T_Tessa_Cards_CardRequest.htm). Он не документирует корпоративный обработчик указанного requestType и не доказывает его исправность.

## Незакрытая ошибка интервалов

Два живых отчёта содержат одинаковый `LeftOperandExtractor is null` для сочетания источника значения в настройке, целочисленного операнда, интервала и сравнения на равенство. Ошибка возвращается до Store. Точную причину внутри серверного обработчика или конфигурации нельзя установить по сохранённому web-клиенту. В 1.9.47 исправлены принятие некорректного ответа и отображение отказа; серверный дефект не объявляется исправленным.

Для разработчика серверной части:

1. Найти обработчик указанного requestType и место формирования `LeftOperandExtractor is null`.
2. Проверить выбор извлекателя для источника настройки + Int + Between и используемое сравнение равенства. Проверить конфигурацию обоих критериев числа листов, не меняя типы данных наугад.
3. Сопоставить отказ при наличии ранее сохранённой строки с пересекающимся набором прочих условий. Разные интервалы должны дать корректный результат бизнес-проверки, даже если по правилам они конфликтуют.
4. Добавить серверные тесты: одинаковые/разные интервалы, пустой критерий, ноль, граничные Int32, несколько значений, существующая строка плюс новое добавление. Ответ должен быть явным разрешением или диагностикой конфликта, а не исключением извлекателя.

Для сравнения с обычным редактором в тестовой матрице: скопировать строку с диапазоном 801–809, поменять диапазон на 810–819 и запустить штатную проверку. Если редактор возвращает ту же ошибку, сохранить полный серверный стек. Если штатная проверка проходит, сравнить её запрос с запросом Studio по типам полей, секциям и конфигурации, не только по видимым подписям. Этот контроль вручную ещё не выполнен.

Не обходить проверку дубликатов, не превращать исключение в `ok=true`, не заменять диапазон одиночным числом ради прохождения. Для следующих проверок использовать свежий экспорт (16); старый смешанный файл уже применялся.

## Автоматические регрессии

`tests/duplicate-validation-contract.mjs` проверяет отсутствие и неверные типы `ok`, отрицательный/положительный ответ, приоритет ошибки платформы, сохранение причин двух отказов после удаления Preview, экранирование HTML и отсутствие повторных запросов при отображении.

`tests/apply-add-race.mjs` проверяет реальный метод Bridge внутри Apply: предварительная проверка успешна, повторная получает дубль, некорректный ответ или ошибку интервалов; Store в каждом случае не вызывается. Остальные правила применения и сверки остаются в общем `npm test`.


## Повторная проверка 1.9.47 и выгрузка (16)

Файл TESSA_FINAL_v1.9.47.xlsx содержит 21 уже сохранённую строку и два ожидающих добавления (Excel 36–37). Локальное сравнение с выгрузкой (16) даёт 21 NOOP и 2 ADD. Живая предварительная проверка переводит оба ADD в SKIP с тем же `LeftOperandExtractor is null`. Кнопка Apply недоступна, Store не запускается. Все 546 ячеек выгрузки (16) совпали с (15); обе новые строки отсутствуют.

Это не доказательство исправления серверной причины. В 1.9.48 исправлено только вводившее в заблуждение отображение: «Все» теперь включает отказы, нет обещания применить ноль изменений, технический текст не повторяется в нескольких блоках.

Следующий контроль нужен в штатном редакторе тестовой матрицы: скопировать сохранённую строку с интервалом 801–809, заменить интервал на 810–819 и вызвать штатную проверку. При том же отказе разработчику нужен серверный стек обработчика проверки дубликатов. Если штатный вариант проходит, необходимо сравнить его типизированный запрос с запросом Studio до изменения сериализации. Без этого контроля причину нельзя уверенно отнести только к настройке, серверному коду или различию запросов.


Для сбора запросов без ручного копирования и без записи доступна [диагностика интервалов 1.9.49](INTERVAL-DIAGNOSTICS.md). Она позволяет отделить проверку исходной сохранённой карточки от её перестройки Studio. Новая выгрузка (17) совпала с (16); успешного добавления этих двух строк по-прежнему нет.
