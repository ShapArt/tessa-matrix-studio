# TESSA Matrix Studio — production runbook

Практический регламент для предрелизной проверки, ограниченного боевого теста, выпуска и отката TESSA Matrix Studio.

## Проверки 1.9.46

[Смешанный прогон и отчёт 1.9.46](UAT-v1.9.46-FRESH-MIXED.md): после Apply и сверки кнопка доступна; неудачный авто-refresh позволяет запустить ручной.

Подключение проверяется автоматически без серверных запросов. До загрузки карточки показывается ожидание, а не несовместимость. «Собрать значения» находится рядом со «Скачать Excel»; обновление справочников и полей — в «Дополнительно», выбор пакета — в «Выбрать часть изменений». Чужая карточка и смена TemplateID инвалидируют старое состояние; preflight повторно проверяет шаблон. [Проверка 1.9.44 и результат живого прогона](UAT-v1.9.44-PICKER-AUDIT.md). Дополнительно проверить отсутствие жёлтых input messages в новой выгрузке, шрифт текущей темы, reduced motion и смешанные ошибки.

## Исправления 1.9.41: поля и диапазоны

Релизный кандидат 1.9.41 исправляет обнаруженные в live UAT 1.9.40 ложные дубли при одинаковых подписях справочника и пропуск всей строки из-за отдельной ячейки. Значение `4-15` теперь записывается как IntValue=4, IntToValue=15. Неоднозначный числовой serial с форматом даты по-прежнему не восстанавливается догадкой.

Только для UPDATE, сопоставленного по identity и прошедшего исходные guards, ошибка отдельного поля исключает этот столбец из rebuild. Текущее значение берётся из snapshot, участвует в проверке дублей и сохраняется при свежем preflight. В Preview, подтверждении Apply и Apply JSON (`skippedFields`) явно указаны исключённые поля. Если не осталось корректных изменений, строка остаётся SKIP. ADD, REPLACE, DELETE и ошибки identity/baseline не превращаются в частичные операции.

Перед выпуском повторить сценарии из [проверки 1.9.41](UAT-v1.9.41-FIELD-FIXES.md). Автоматические тесты и локальная имитация браузера не подтверждают запись в корпоративную TESSA.

## 1. Что считаем готовностью к боевому тесту

Перед тестированием на рабочей TESSA должны одновременно выполняться условия:

- ветка выпуска прошла `npm test` и CodeQL;
- production-userscript установлен из GitHub Release, а не из случайной локальной копии;
- версия в Tampermonkey совпадает с ожидаемой версией Studio;
- первая проверка выполняется на матрице/версии, где контролируемое изменение допустимо;
- перед каждым независимым сценарием используется свежая выгрузка Excel;
- исходный Excel сохраняется отдельно как резервная копия;
- пользователь заранее знает ожидаемые счётчики Preview;
- любой неожиданный DELETE, REPLACE или массовый diff является стоп-сигналом.

## 2. Перед началом

Начиная с v1.9.40 сначала посмотрите строку совместимости в закреплённом status-блоке Studio:

- **Матрица готова** — обязательные возможности для текущей карточки доступны;
- **Есть ограничения / Только чтение** — отсутствует необязательная возможность, блокируется только зависимая операция;
- **Подключение недоступно** — отсутствует обязательный read/write primitive или надёжный контекст открытой матрицы, соответствующая операция должна fail-closed остановиться.

Capability gate считается **по фактически выбранным операциям**. Отсутствие возможности создать новую строку блокирует ADD, но не UPDATE-only Apply; отсутствие локального refresh представления не отменяет успешно записанные изменения и не запрещает Apply. Автопроверка и кнопка **«Проверить подключение»** перечитывает только локальные возможности текущей web-сессии и не делает Store/Delete.

1. Открыть Tampermonkey и проверить, что включён только один экземпляр `TESSA Matrix Studio — Черкизово`.
2. Проверить версию скрипта.
3. Обновить страницу TESSA (`Ctrl+R`).
4. Убедиться, что панель Studio появилась и открыта нужная карточка матрицы.
5. Скачать свежий Excel.
6. Сохранить копию выгрузки без изменений.
7. Если недавно менялись справочники, использовать выгрузку **со свежими справочниками**.

Не используйте старый Excel после того, как матрица уже была изменена в TESSA. Следующий сценарий начинается с новой выгрузки.

## 3. Как читать Preview

Preview — это план, а не запись.

Проверяются четыре вещи:

- тип операции: ИЗМЕНИТЬ / ДОБАВИТЬ / ЗАМЕНИТЬ / УДАЛИТЬ;
- количество операций;
- конкретная строка/поля;
- `ПРОПУСТИТЬ` и причина skip.

Если пользователь ожидал UPDATE одной строки, а Preview показывает DELETE, REPLACE или десятки изменений — Apply не нажимать.

Начиная с v1.9.20 Preview выполняет read-only preflight на свежей TESSA. Поэтому невалидный справочник, дубль, stale-конфликт и зависимый DELETE должны быть видны до Apply как skip/blocker.

Начиная с v1.9.32 большой Preview просматривается постранично. Фильтры `Все / Изменить / Добавить / Удалить / Пропустить` и поиск применяются ко всему плану, а не только к текущей странице. Перед массовым Apply пользователь обязан проверить все релевантные страницы либо сузить план фильтром и selective review.

## 4. Перед Apply

Apply допустим только когда Preview соответствует намерению пользователя.

Перед записью Studio самостоятельно выполняет второй свежий preflight. Это защита от ситуации, когда после Preview другой пользователь успел изменить матрицу.

Для DELETE отдельного browser-confirm больше нет: количество удалений видно в общем подтверждении Apply, а конкретные DELETE нужно проверить в Preview. Destructive guards, свежий preflight и финальный target recheck перед удалением остаются обязательными.

Operational limits v1.9.32:

- до 500 mutation-операций — штатный Apply;
- 501–2000 mutation-операций — обязательное дополнительное подтверждение большого пакета;
- более 2000 mutation-операций — hard block до создания TESSA bridge; пакет нужно разделить;
- 100 и более DELETE — hard block независимо от доли матрицы;
- прежний ratio guard сохраняется: 10 и более DELETE при удалении не менее 20% исходной матрицы блокируются.

Начиная с v1.9.36 большой Preview можно сузить прямо в Studio через **«Выбрать часть изменений»**. Выберите `Все / Изменить / Добавить / Удалить`, при необходимости задайте поиск, затем оставьте `1 / 10 / 100 / 500 / 2000` операций. Пакет формируется обычными review-exclusions: исходный Excel не переписывается, **«Вернуть всё»** восстанавливает полный Preview, а перед реальной записью выбранный пакет всё равно проходит свежий server preflight.

В Roundtrip V6 не объединяйте физический DELETE и новые строки без hidden identity в одном Excel. Missing baseline identity вместе с no-identity ADD намеренно fail-closed считается неоднозначностью. Для DELETE и ADD используйте отдельные свежие выгрузки.

## 5. После Apply

После любого изменения:

1. дождаться итогового статуса Studio;
2. при необходимости диагностики открыть **«Дополнительно → Скачать отчёт»** — JSON больше не создаётся автоматически; сохранить его до перезагрузки вкладки;
3. скачать **новую** выгрузку Excel либо вручную обновить страницу TESSA;
4. проверить, что свежая выгрузка соответствует подтверждённому Preview;
5. убедиться, что соседние/исходные строки не изменились;
6. только после этого переходить к следующему сценарию.

Начиная с v1.9.37 Studio намеренно **не вызывает принудительный `refreshCard()` сразу после Store/Delete**. Живой UAT показал, что нативное представление в этот момент может быть занято writer-lock, хотя сами Store уже завершились успешно. После первой начатой записи старый Preview автоматически инвалидируется и повторный Apply невозможен до новой проверки.

### Read-only проверка результата в v1.9.40

После реально завершившихся mutation-операций Studio хранит **только в памяти текущей вкладки** private receipt-контекст. Он содержит plan/matrix/template identity и по одной записи на успешно завершённый UPDATE/ADD/DELETE. Для UPDATE/ADD сохраняется stable target identity и hash ожидаемого ID-first typed-state; для DELETE — target row/version identity. Receipts не восстанавливаются после перезагрузки вкладки и не добавляются в обычный Apply JSON.

Кнопка **«Проверить результат»** выполняет отдельное fresh read и не является продолжением Apply:

- `verified` — все проверяемые receipts подтверждены;
- `divergent` — найдена семантическая разница, ожидаемая строка исчезла либо DELETE-target всё ещё присутствует в текущем membership;
- `incomplete` — часть результата нельзя доказать по identity или fresh read не завершился.

UPDATE/ADD подтверждаются только по точной RowCardID/VersionID identity и ожидаемому semantic hash. **Semantic nearest-match запрещён**: похожая строка не может быть принята за созданную/обновлённую. DELETE считается подтверждённым только когда обе сохранённые target identity отсутствуют в свежем membership; если тот же RowCardID остался с другой версией, результат divergent.

Fresh snapshot индексируется один раз по RowCardID и VersionID; последующая сверка receipts работает O(N+M), без полного `.find()` по snapshot для каждой операции.

При transient writer-lock reconciliation делает максимум **3 попытки**: сразу, затем через **450 мс**, затем через **900 мс**. Другие ошибки не ретраятся вслепую. Reconciliation никогда не делает Store/Delete, не вызывает rollback и не пытается автоматически исправить `divergent`/`incomplete`; следующий write начинается только с нового Preview.

Если Apply завершился частично, не повторяйте старый Apply вслепую. Скачайте свежее состояние и заново постройте Preview.

Кнопка Stop не является rollback. Уже завершённые `CardStore`/DELETE остаются в TESSA. Начиная с v1.9.32 итоговый JSON фиксирует точную границу: `status`, `plannedCount`, `startedCount`, `appliedCount`, `skippedCount`, `failedCount`, `notStartedCount` и `cancelled`. После `status=cancelled` продолжать старый план нельзя — нужна свежая выгрузка.

## 6. Стоп-критерии

Немедленно прекратить применение изменений, если наблюдается хотя бы одно:

- неожиданный DELETE;
- REPLACE не той строки;
- количество операций не совпадает с ожидаемым;
- строка, отмеченная как SKIP, всё равно изменилась в TESSA;
- prerequisite UPDATE/ADD пропущен или упал, но связанный DELETE выполнился;
- stale-конфликт не блокирует старые значения;
- Cancel/отказ в подтверждении приводит к записи;
- после Apply свежая выгрузка отличается от подтверждённого Preview;
- появляются ошибки, похожие на потерю identity/MatrixRowID/MatrixVersionID/baseline;
- Studio показывает массовые изменения после обычной сортировки Excel.

В таком случае сохранить свежую выгрузку, JSON-отчёт, версию Studio и обезличенный скрин Preview. Не публиковать рабочий Excel и внутренние данные в публичном Issue.

## 7. Что делать при ошибке

Studio не скачивает диагностические JSON автоматически. После Apply или необработанной ошибки последний отчёт хранится только в памяти текущей вкладки; если он нужен для разбора, пользователь явно нажимает **«Скачать отчёт»**.

Для отдельного support-объекта v1.9.40 действует whitelist: версия Studio, capability `code/scope`, счётчики Apply, счётчики/status/reason codes reconciliation. Workbook, snapshot, private receipts/hash, raw logs/error и business/display values туда не копируются. MatrixID/TemplateID допускаются только при явном `includeIds=true` и только во внутреннем безопасном канале. Это отдельный безопасный формат; обычный Apply JSON не был переопределён этой функцией.

Для диагностики нужны:

- версия Studio;
- браузер и версия Tampermonkey;
- что пользователь хотел изменить;
- счётчики Preview;
- тип проблемной операции;
- текст friendly/technical error;
- обезличенный скрин;
- свежая выгрузка — только через внутренний безопасный канал, если она действительно нужна.

Перед повторной попыткой всегда перечитывать матрицу и строить новый Preview.

## 8. Выпуск новой версии

Production userscript меняется только вместе с увеличением `@version` и `APP.version`.

Обычный путь:

1. feature/fix branch;
2. RED regression-test для изменяемого поведения;
3. минимальный fix;
4. полный `npm test`;
5. Pull Request;
6. успешные Tests + CodeQL;
7. merge в `main`;
8. Release workflow повторно проверяет код и публикует новый release;
9. workflow проверяет публичные latest assets и SHA-256;
10. Delivery Canary продолжает ежедневную проверку.

CI запрещает повторную публикацию той же версии, но GitHub Release Immutability является отдельной настройкой репозитория. Перед production-релизом в **Settings → Releases** должна быть включена **Release Immutability**. Если она не включена, не называйте release immutable только на основании SHA-256/CI.

Повторно публиковать существующую версию нельзя. Если release уже существует, нужно увеличивать версию, а не перезаписывать asset.

## 9. Быстрый откат

Если обнаружен production-дефект до выпуска исправления:

### Самый безопасный немедленный вариант

Отключить TESSA Matrix Studio в Tampermonkey. Нативная TESSA продолжит работать без userscript.

### Возврат к предыдущему релизу

Можно вручную установить userscript из предыдущего проверенного GitHub Release. Если требуется удерживать старую версию, временно отключить автоматическую установку обновлений Tampermonkey для Studio; иначе `latest` снова предложит новую версию.

После фикса выпустить **новую** версию. Не перезаписывать дефектный release тем же tag/version.

## 10. Изменения CI и supply chain

Внешние GitHub Actions должны быть указаны только полным 40-символьным commit SHA. Плавающие `@v4`, `@v7`, `@main` запрещены regression-тестом.

Dependabot следит за `github-actions` и создаёт PR для обновления pin-значений. Такие PR проходят те же Tests/CodeQL и должны проверяться как обычные изменения supply chain.

Не заменять SHA обратно на tag «для удобства».

## 11. Минимальный чек после обновления TESSA

Studio использует внутренние объекты страницы TESSA через `TessaBridge`. Поэтому после крупного обновления TESSA нужно отдельно проверить:

- создание bridge;
- получение структуры матрицы;
- snapshot строк;
- `CardGet` существующей строки;
- `CardNew` новой строки;
- duplicate validation;
- безопасный `CardStore` на тестовой/черновой строке;
- штатный delete request на специально подготовленной тестовой строке;
- refresh после Apply.

Если изменился внутренний API TESSA, правка должна оставаться внутри `TessaBridge`, а planner/UI по возможности не меняться.

## 12. Аудит выгрузок матриц

Для массовой предрелизной проверки выгрузок собирается отдельный набор свежих `.xlsx`. Для каждой книги фиксируются:

- Roundtrip format;
- Matrix ID / Template ID;
- наличие и целостность baseline-ledger;
- количество рабочих строк;
- дубли MatrixRowID / MatrixVersionID;
- отсутствие повреждённой служебной схемы;
- NOOP-результат для неизменённой свежей выгрузки;
- отсутствие неожиданных ADD/DELETE/REPLACE.

Если выгрузки получены в разное время и матрицы после этого менялись, их нельзя считать единым актуальным snapshot для Apply — для записи всё равно нужна свежая выгрузка конкретной матрицы.

## Post-Apply отображение и результат

Начиная с v1.9.39 успешный Store отделён от обновления UI. После mutation Studio обновляет только нативное представление матрицы, не выполняя полный `editor.refreshCard()`. Для transient writer-lock (`ObtainWriterLock` / `WriteHeartbit`) выполняется ограниченный retry; если view всё равно не обновился, Store-result не меняется и пользователь может нажать **«Обновить отображение»** вручную.

Source-skipped строки, исключённые planner/source validation до mutation-plan, показываются отдельно и не делают успешный Apply частичным. `partial` используется только для незавершённого mutation-plan: preflight/store skip, not-started, cancel или неполная verification. После любой начавшейся mutation старый Preview остаётся consumed; перед следующим Apply нужна свежая проверка/выгрузка.

Progress/status панели закреплён сверху внутри её scroll-container, чтобы этап, процент и ETA не терялись при длинном Preview.
