# Алгоритмы ADD, UPDATE и DELETE

Этот документ описывает, как TESSA Matrix Studio 1.17.1 превращает Excel в проверяемый план. Номер строки Excel используется только для сообщения пользователю. Идентичность существующей строки задают скрытые `RowCardID`, `VersionID` и baseline fingerprint.

## Общий конвейер

1. Studio проверяет ZIP/OOXML-лимиты, запрещённые пути, формулы в рабочих ячейках, формат roundtrip и принадлежность файла матрице/шаблону.
2. Служебная схема сопоставляется с текущей структурой матрицы. Неизвестные и удалённые столбцы не угадываются.
3. Видимые значения разрешаются в стабильные ID справочников. Неоднозначность, отсутствующий ID или неполный справочник дают `SKIP` либо блокируют атомарный перенос.
4. Planner строит `KEEP`, `ADD`, `UPDATE`, `DELETE` и `SKIP` без записи.
5. Перед Apply Studio повторно читает затронутые строки, проверяет версии, ACL, дубли, типы документов и writer lock.
6. Результат считается подтверждённым только после server receipt и повторного read-back. Принятая сервером операция и подтверждённое состояние показываются отдельно.

## ADD

Строка считается новой, когда у неё нет валидной identity существующей строки. Копирование старой строки поддерживается: если пользователь изменил бизнес-значения и вставил копию ниже, lifecycle-анализ не переиспользует скрытый ID как разрешение перезаписать оригинал.

Для ADD обязательны:

- уникальная комбинация критериев и исполнителей;
- актуальные справочные ID;
- вид документа из области `CardTypeID` шаблона;
- успешный `CardNew`/duplicate preflight и право сервера на создание;
- receipt с новым `RowCardID`, по которому выполняется read-back и возможный cleanup.

Full UAT может копировать историческую строку, где старый вид документа допустимо сохранить, но нельзя назначить заново. Перед тестовым ADD runner заменяет такой вид на значение из актуального CardTypeID-scoped каталога. Production safety boundary остаётся fail-closed.

## UPDATE

UPDATE строится, когда `RowCardID`/`VersionID` однозначно указывают на существующую строку, а нормализованный fingerprint рабочих полей изменился. В `changes` попадают только реальные различия `before → after`.

Перед записью проверяются:

- строка всё ещё принадлежит открытой матрице;
- версия и baseline не устарели;
- текущий пользователь имеет право чтения и записи;
- новые справочные значения существуют и допустимы;
- изменение не создаёт бизнес-дубль.

Историческое значение вида документа разрешено оставить без изменения. Новое назначение проверяется по актуальному типу карточки.

## DELETE

DELETE появляется, когда существующая строка из baseline физически удалена из Excel либо все её рабочие поля очищены. Простая пустая строка без identity удалением не считается.

Перед удалением Studio заново проверяет membership и версию целевой строки. DELETE выполняется только после успешной подготовки зависимых ADD/UPDATE. Первая ошибка в фазе удаления останавливает следующие удаления; итог получает `partial`/`unsafe`, пока read-back не докажет фактическое состояние.

## Копия поверх существующей строки

Если пользователь вставил копию поверх другой строки, lifecycle-анализ разделяет identity позиции и бизнес-содержимое. Preview явно показывает замену/обновление либо блокирует неоднозначный случай. Скрытые ID из скопированных ячеек сами по себе не дают права менять или удалять другую строку.

## Ограничения Apply

- жёсткий предел — 2 000 исполняемых операций;
- предупреждение — от 500 операций;
- большие переносы остаются атомарными на этапе preflight;
- клиент не является механизмом авторизации: запрет `CardGet`, `CardNew`, `CardStore` и удаления обязан применить сервер TESSA.
